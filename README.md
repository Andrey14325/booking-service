# Booking Service

Backend-сервис бронирования событий с ограниченным количеством мест (билеты на концерт, слоты на курс и т.п.), написанный на Go. Ключевая инженерная задача — гарантировать, что при большом количестве одновременных запросов количество подтверждённых броней никогда не превысит доступное число мест (защита от overselling).

## Стек

- **Go** 1.26, стандартная библиотека `net/http` (без веб-фреймворков)
- **PostgreSQL 16** — хранилище данных, через драйвер `pgx/v5`
- **golang-migrate** — версионирование схемы БД
- **Docker / docker-compose** — локальный запуск и деплой

## Архитектура

Проект разделён на слои с однонаправленной зависимостью:

- **`handlers`** — разбор HTTP-запросов/ответов, ничего не знает про SQL
- **`service`** — бизнес-логика и валидация, не знает ни про HTTP, ни про SQL
- **`storage`** — SQL-запросы к Postgres, ничего не знает про HTTP

Каждый слой взаимодействует с соседним снизу через интерфейс, а не через конкретный тип — это позволяет тестировать `service` и `handlers` через mock-объекты, без поднятия реальной БД (см. раздел «Тесты»).

## Защита от overselling

Самое важное архитектурное решение в проекте. При бронировании (`POST /api/v1/events/{id}/reserve`) выполняется следующая транзакция:

```sql
BEGIN;
SELECT available_slots FROM events WHERE events_id = $1 FOR UPDATE;
-- проверка: available_slots > 0
UPDATE events SET available_slots = available_slots - 1 WHERE events_id = $1;
INSERT INTO reservations (...) VALUES (...);
COMMIT;
```

`SELECT ... FOR UPDATE` блокирует строку события до конца транзакции. Если два запроса одновременно пытаются забронировать последнее место, второй запрос **ждёт** завершения первого и видит уже актуальный (уменьшенный) остаток мест — гонки состояний не возникает.

Альтернатива, которую я рассматривал — optimistic locking через поле `version` с retry на конфликт. `FOR UPDATE` был выбран как более простой в реализации вариант, приемлемый при умеренной нагрузке; при высокой конкуренции за один и тот же ряд optimistic locking масштабируется лучше за счёт отсутствия блокировок.

Проверено нагрузочным тестом (`cmd/loadtest`) — 20 параллельных горутин, бронирующих событие с 5 местами, дают ровно 5 успешных броней и 15 отказов, независимо от порядка выполнения.

## Прочие возможности

- **Idempotency-Key** — заголовок `Idempotency-Key` при бронировании защищает от повторного создания брони при retry на клиенте (например, из-за обрыва сети). Повторный запрос с тем же ключом и тем же событием возвращает id уже созданной брони, а не создаёт новую.
- **Фоновый воркер** — раз в 30 секунд находит брони со статусом `pending`, у которых истёк `expires_at` (10 минут по умолчанию), переводит их в `expired` и возвращает место в пул доступных.
- **Graceful shutdown** — сервер корректно завершает обработку активных запросов при `SIGINT`/`SIGTERM`, с таймаутом на принудительное закрытие.

## API

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/health` | Проверка живости сервиса |
| `POST` | `/api/v1/events` | Создать событие (`name`, `total_slots`) |
| `GET` | `/api/v1/events/{id}` | Получить событие по id |
| `POST` | `/api/v1/events/{id}/reserve` | Забронировать место (`user_id`, опционально заголовок `Idempotency-Key`) |

Пример запроса:
```bash
curl -X POST localhost:8080/api/v1/events -d '{"name":"Concert","total_slots":10}'
curl -X POST localhost:8080/api/v1/events/{id}/reserve -H "Idempotency-Key: unique-key-1" -d '{"user_id":"alice"}'
```

## Запуск

Требуется установленный Docker.

```bash
docker-compose up --build
```

Это поднимет Postgres, автоматически применит миграции и запустит сервис на `localhost:8080`. Проверка:
```bash
curl -i localhost:8080/health
```

## Тесты

```bash
go test ./... -v
```

Юнит-тесты покрывают слои `service` и `handlers` через mock-реализации интерфейсов (без реальной БД) — проверены все ветки бизнес-логики: валидация, успешные сценарии, обработка ошибок (`404`/`409`/`400`/`500`).
